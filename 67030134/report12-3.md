## 2. สรุปผลและคำถามท้ายการทดลอง (Review Questions)

### ข้อ 1: เหตุใดการใช้ `TweenAnimationBuilder` จึงทำให้เข็มมาตรวัดดูนุ่มนวลและไม่กระตุก แม้ข้อมูลเซนเซอร์จะเข้ามาทุกๆ 500 มิลลิวินาที?
* **คำตอบ:**
  * **การคำนวณค่าระหว่างทางอัตโนมัติ (Linear/Curved Interpolation - Lerp):** ข้อมูลดิบจากเซนเซอร์ที่ส่งผ่าน MQTT มีลักษณะเป็นค่าแบบกระโดดเป็นขั้นๆ (Discrete Steps) ทุกๆ 500ms หากนำค่านี้ไปวาดเข็มโดยตรง เข็มจะกระตุกข้ามช่องทันที แต่การใช้ `TweenAnimationBuilder<double>` จะทำการสร้างการเปลี่ยนผ่านของค่าจาก `begin` (ค่าเดิม) ไปยัง `end` (ค่าใหม่ที่เพิ่งได้รับ) ในช่วงระยะเวลาที่กำหนด (เช่น 400ms) โดยคำนวณจุดพิกัดย่อยระหว่างทางให้อัตโนมัติในทุกๆ เฟรม
  * **การเรนเดอร์ระดับ 60–120 FPS ร่วมกับ Animation Curves:** Flutter Engine จะเรนเดอร์ภาพที่อัตราความถี่สูงของหน้าจอสมาร์ตโฟน (60Hz ถึง 120Hz) การใช้ Curves เช่น `Curves.easeOutCubic` ช่วยให้เข็มเร่งความเร็วและค่อยๆ ผ่อนลงอย่างนุ่มนวลตามหลักฟิสิกส์ ทำให้สายตาของผู้ใช้งานมองเห็นการหมุนของเข็มที่เรียบเนียน ไม่สะดุดตา แม้ช่วงเวลาการรับแพ็กเก็ตจากเครือข่ายจะมีความไม่สม่ำเสมอ (Jitter) ก็ตาม

### ข้อ 2: การจำกัดความยาวของอาร์เรย์ `_history` ให้เก็บไม่เกิน 30 ตัวอย่าง ส่งผลดีต่อประสิทธิภาพหน่วยความจำของสมาร์ตโฟนอย่างไร?
* **คำตอบ:**
  * **ป้องกันปัญหาหน่วยความจำรั่วไหลและขนาดอาร์เรย์ไม่สิ้นสุด (Preventing Memory Leak & Unbounded Growth):** ในระบบ IoT ที่ทำงานตลอด 24 ชั่วโมง หากรับข้อมูลทุกๆ 500ms ใน 1 วันจะมีข้อมูลไหลเข้ามามากถึง 172,800 ค่า หากไม่มีการจำกัดขนาด อาร์เรย์จะกินพื้นที่ RAM ในโทรศัพท์เพิ่มขึ้นเรื่อยๆ จนระบบปฏิบัติการบังคับปิดแอปพลิเคชัน (Out-Of-Memory Crash) การใช้เทคนิค Rolling Buffer หรือ Sliding Window โดยตัดข้อมูลตัวแรกออก (`_history.removeAt(0)`) เมื่อขนาดเกิน 30 ค่า จะทำให้ขนาดหน่วยความจำคงที่เสมอ
  * **รักษาความเร็วในการวาดกราฟให้อยู่ในระดับคงที่ (Constant O(1) Rendering Complexity):** คอมโพเนนต์ `CustomPainter` จะต้องวนลูปคำนวณจุดพิกัด `(x, y)` เพื่อวาดเส้นลงบน Canvas ในทุกๆ เฟรม หากมีข้อมูลเพียง 30 จุด การประมวลผลคำนวณ Path จะใช้เวลาเพียงเสี้ยววินาที ทำให้ GPU ทำงานเบา ไม่เกิดเฟรมดรอป (Frame Drops) และไม่สูบแบตเตอรี่ของสมาร์ตโฟน

### ข้อ 3: หากเซนเซอร์ส่งค่าผิดพลาด เช่น ค่านอกช่วง 0 - 3.3V หรือค่าเป็น `null` โค้ดส่วนใดใน `telemetry_dashboard_screen.dart` ที่ช่วยป้องกันไม่ให้แอปแครช?
* **คำตอบ:**
  * **1. การดักจับข้อผิดพลาดด้วยบล็อก `try-catch`:**
    ในฟังก์ชันรับข้อความ มีการครอบกระบวนการแปลงข้อมูลสตริงด้วยบล็อก `try { ... } catch (e) { ... }` หากเพย์โหลดที่ได้รับไม่ใช่ JSON ที่ถูกต้อง หรือเกิดปัญหาการถอดรหัส ตัวแปรจะไม่ทำให้โปรเซสหลักหยุดทำงาน (App Crash) แต่จะดักจับข้อผิดพลาดและปล่อยผ่านอย่างปลอดภัย
  * **2. การใช้ Null-aware Casting และ Null-coalescing Operator (`as num?`, `?.`, `??`):**
    ในขั้นตอนดึงค่าจาก Map มีการเขียนในรูปแบบ `final voltage = (data['voltage'] as num?)?.toDouble() ?? 0.0;` ซึ่งป้องกันปัญหา `TypeError` กรณีคีย์ `voltage` ไม่มีอยู่จริงหรือมีค่าเป็น `null` โดยระบบจะกำหนดค่าดีฟอลต์เป็น `0.0` ทันที
  * **3. การจำกัดขอบเขตค่าด้วยเมธอด `.clamp(0.0, 1.0)`:**
    ทั้งใน `_SparklinePainter` และ `_GaugePainter` มีการคำนวณอัตราส่วนสเกลโดยใช้ `.clamp(0.0, 1.0)` เช่น `((history[i] / maxLimit).clamp(0.0, 1.0) * size.height)` หากเซนเซอร์ส่งค่าผิดปกติ เช่น ติดลบ หรือพุ่งเกิน 3.3V (เช่น สัญญาณรบกวน 5.0V) เมธอด `.clamp()` จะบังคับให้ผลลัพธ์ไม่เกินขอบเขต 0.0 ถึง 1.0 เสมอ จึงป้องกันไม่ให้เส้นกราฟหรือเข็มมาตรวัดวาดทะลุออกนอกพื้นที่ของวิดเจ็ต
