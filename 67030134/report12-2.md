## 1. ผลลัพธ์การทดลอง (Experimental Results)

### 1.1 การจำลองและทดสอบการควบคุมสองทางผ่าน PowerShell CLI
- **การจำลองส่งสถานะ Online ของ ESP32:**
```powershell
mosquitto_pub -h 127.0.0.1 -p 1883 -t "iot/esp32/status" -m "online" -r
```
*ผลลัพธ์:* แถบสถานะด้านบนของหน้าจอ Flutter เปลี่ยนเป็นสีเขียว `ESP32 เชื่อมต่อแล้ว (ONLINE)` และปุ่มสวิตช์เปิดใช้งานได้

- **การดักฟังคำสั่งควบคุมจากแอปพลิเคชัน:**
```powershell
mosquitto_sub -h 127.0.0.1 -p 1883 -t "iot/esp32/control" -v
```
*ผลลัพธ์:* เมื่อกดเปิดสวิตช์บน Flutter แอปส่งข้อความ `{"command":"ON"}` หรือ `{"led":"ON"}` ออกมายังเทอร์มินัลทันที

- **การส่งสัญญาณ ACK จำลองการยืนยันจากฮาร์ดแวร์จริง:**
```powershell
mosquitto_pub -h 127.0.0.1 -p 1883 -t "iot/esp32/led_ack" -m '{"led_state": true, "ack": true}'
```
*ผลลัพธ์:* สวิตช์และไอคอนหลอดไฟบนแอปเปลี่ยนเป็นสีเขียวสว่าง พร้อมเปิดไฟสถานะจริง

- **การจำลองสภาวะบอร์ดตัดการเชื่อมต่อหรือไฟดับ (LWT):**
```powershell
mosquitto_pub -h 127.0.0.1 -p 1883 -t "iot/esp32/status" -m "offline" -r
```
*ผลลัพธ์:* ป้ายสถานะเปลี่ยนเป็นสีแดง `ESP32 ออฟไลน์ (OFFLINE)` สวิตช์ถูกล็อก (Disabled) ป้องกันการส่งคำสั่งผิดพลาด

## 2. สรุปผลและคำถามท้ายการทดลอง (Review Questions)

### ข้อ 1: ประโยชน์ของการรอสัญญาณ ACK จากหัวข้อ `iot/esp32/led_ack` แทนการเปลี่ยน UI ทันที (Optimistic Update) คืออะไร?
* **คำตอบ:**
  * **ความสอดคล้องกับสถานะจริงทางกายภาพ (True Physical State Synchronization):** ในระบบ IoT ทางอุตสาหกรรมหรือสมาร์ตโฮม การที่ผู้ใช้กดสวิตช์บนแอปไม่ได้แปลว่าอุปกรณ์ฮาร์ดแวร์ปลายทางจะทำงานสำเร็จเสมอไป (เช่น สัญญาณ Wi-Fi ปลายทางอาจหลุด, วงจร Relay ขัดข้อง, หรือสายไฟขาด) การรอสัญญาณ ACK ยืนยันจากฮาร์ดแวร์จริงก่อนปรับ UI จะป้องกันไม่ให้ผู้ใช้เข้าใจผิดว่าอุปกรณ์เปิดอยู่ ทั้งที่ความจริงอุปกรณ์ปลายทางยังไม่ตอบสนอง
  * **การป้องกันคำสั่งค้างและการกดย้ำ (Debouncing / Prevention of Conflicting State):** หากใช้การเปลี่ยนสถานะทันที (Optimistic UI) แล้วคำสั่งส่งไปไม่ถึง จะเกิดสภาวะ Desynchronization ทำให้สถานะบนหน้าจอกับอุปกรณ์จริงขัดแย้งกัน การรอ ACK ช่วยให้แอปสามารถตั้งเวลา Timeout ได้ หากไม่มี ACK ตอบกลับภายในเวลาที่กำหนด แอปสามารถเด้งกลับไปยังสถานะเดิมและแจ้งเตือนผู้ใช้ได้อย่างถูกต้อง
  * **ความน่าเชื่อถือและความปลอดภัยในระบบ IoT (System Integrity & Safety):** สำหรับอุปกรณ์สั่งการที่อันตราย เช่น ประตูไฟฟ้า ปั๊มน้ำ หรือฮีตเตอร์ การทราบสถานะที่แท้จริงตามฮาร์ดแวร์ (Closed-loop Verification) เป็นมาตรฐานความปลอดภัยที่จำเป็นอย่างยิ่ง

### ข้อ 2: ทำไมเราจึงควรตั้งแฟล็ก Retain (`-r`) สำหรับหัวข้อสถานะ `iot/esp32/status`?
* **คำตอบ:**
  * **การซิงโครไนซ์สถานะทันทีเมื่อเปิดแอปพลิเคชัน (Instant Initial State Synchronization / Cold-start Dashboard):** 
    เมื่อเปิดแอป Flutter ขึ้นมาใหม่ แอปเพิ่งจะทำการบอกรับ (Subscribe) หัวข้อ `iot/esp32/status` หากไม่ได้ตั้งแฟล็ก Retain ไว้ Broker จะไม่มีข้อมูลส่งให้ ทำให้แอปไม่ทราบว่า ESP32 ในขณะนั้นออนไลน์หรือออฟไลน์อยู่ จนกว่าบอร์ดจะวนลูปส่งข้อความใหม่มา แต่เมื่อตั้งค่าแฟล็ก Retain (`-r`) Mosquitto Broker จะเก็บข้อความสถานะล่าสุดเอาไว้ในหน่วยความจำ และจะส่งข้อความสถานะล่าสุดนั้นให้กับ Client ใหม่ที่เพิ่ง Subscribe ทันที โดยที่บอร์ดไม่ต้องส่งซ้ำ
  * **การทำงานร่วมกับกลไก LWT (Last Will and Testament) ได้อย่างสมบูรณ์แบบ:** 
    เมื่อ ESP32 เชื่อมต่อสำเร็จ มันจะ Publish ข้อความ `online` พร้อม Retain Flag เอาไว้ และลงทะเบียน LWT ด้วยข้อความ `offline` พร้อม Retain Flag เช่นเดียวกัน หากบอร์ดเกิดไฟดับ กะพริบ หรือตัดการเชื่อมต่ออย่างกะทันหัน Broker จะนำข้อความ LWT (`offline`) มาแทนที่ข้อความ Retain เดิมทันที ทำให้แอปพลิเคชันใดๆ ก็ตามที่เปิดเข้ามาหลังจากนั้น ทราบได้ทันทีว่าอุปกรณ์ออฟไลน์ไปแล้วโดยไม่ต้องเดา
