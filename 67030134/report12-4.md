## 2. สรุปผลและคำถามท้ายบทเรียน (Review Questions)

### ข้อ 1: เหตุใดการใช้ `IndexedStack` ใน `MainNavigationShell` จึงมีความสำคัญอย่างยิ่งสำหรับแอปพลิเคชัน IoT แบบ Multi-tab เมื่อเทียบกับการสลับวิดเจ็ตด้วย `body: _pages[_currentIndex]`?
* **คำตอบ:**
  * **การรักษาชีวิตของ State และการเชื่อมต่อเครือข่าย (State & Connection Persistence):**
    หากใช้การสลับหน้าแบบ `body: _pages[_currentIndex]` วิดเจ็ตของหน้าที่ไม่ได้แสดงจะถูกทำลายทิ้ง (Dispose) จาก Widget Tree ทันที ทำให้ตัวแปร State, สตรีมการเชื่อมต่อ MQTT Client, Subscription Listener และสถานะการทำงานต่างๆ ถูกรีเซ็ตใหม่ทั้งหมดทุกครั้งที่ผู้ใช้สลับแท็บ
  * **การรักษาข้อมูลประวัติย้อนหลังและการทำงานเบื้องหลัง (Continuous Data Buffering):**
    การใช้ `IndexedStack` จะรักษาวิดเจ็ตทุกหน้าไว้ในหน่วยความจำ โดยซ่อนเฉพาะการแสดงผลเชิงภาพ (Offstage) ส่งผลให้หน้าจอ Telemetry ยังคงทำงานอยู่เบื้องหลัง สามารถรับข้อมูลเซนเซอร์ เก็บข้อมูลลงในอาร์เรย์ `_history` และคำนวณสถิติได้อย่างต่อเนื่อง แม้ว่าในขณะนั้นผู้ใช้จะกำลังสลับไปเปิดหน้าควบคุมสวิตช์ (Actuator Tab) อยู่ก็ตาม เมื่อสลับกลับมากราฟจะยังคงมีข้อมูลต่อเนื่องไม่ขาดตอน

### ข้อ 2: เมื่อเปรียบเทียบการพัฒนาด้วย Flutter ในสัปดาห์นี้ กับการเปิดหน้าเว็บ HTTP บนเบราว์เซอร์ในสัปดาห์ที่ 8-10 ข้อใดให้ประสบการณ์การใช้งาน (UX) และความเสถียรที่ดีกว่าเมื่อข้อมูลเซนเซอร์มาด้วยความถี่สูง? เพราะเหตุใด?
* **คำตอบ:**
  * **แอปพลิเคชัน Flutter ร่วมกับโปรโตคอล MQTT ให้ประสบการณ์การใช้งาน (UX) และความเสถียรที่เหนือกว่าอย่างชัดเจน** ด้วยเหตุผลสำคัญดังนี้:
    1. **ประสิทธิภาพโปรโตคอลเครือข่าย (Protocol Overhead & Efficiency):** 
       MQTT ทำงานผ่านการเชื่อมต่อ Persistent TCP เพียงเซสชันเดียว และมีขนาด Header เริ่มต้นเพียง 2 ไบต์ โดยใช้สถาปัตยกรรมแบบ Event-Driven (Push model) ทันทีที่เซนเซอร์มีข้อมูลใหม่ ข้อมูลจะถูกผลักส่งมายังแอปทันที ในขณะที่ HTTP แบบดั้งเดิมในสัปดาห์ที่ 8-10 มี Header ขนาดใหญ่ (หลายร้อยไบต์) และหากใช้วิธีดึงข้อมูลซ้ำๆ (HTTP Polling) ทุก 500ms จะสร้างภาระให้กับไมโครคอนโทรลเลอร์ ESP32 อย่างมหาศาลจนเกิดปัญหาค้างหรือหน่วยความจำเต็ม
    2. **ประสิทธิภาพการเรนเดอร์กราฟิกและการตอบสนองระดับฮาร์ดแวร์ (GPU Native Rendering):** 
       Flutter คอมไพล์ซอร์สโค้ดเป็น Native Machine Code (ARM/x86) และใช้เอนจินกราฟิก (Impeller/Skia) ในการวาดภาพบน GPU โดยตรง ทำให้สามารถแสดงผล CustomPainter, Radial Gauge และแอนิเมชันความเร็วสูงถึง 60–120 FPS ได้อย่างลื่นไหล ไม่กระตุก ต่างจากเว็บเบราว์เซอร์ที่ต้องพึ่งพาการอัปเดต Document Object Model (DOM) ที่กินทรัพยากรสูงกว่า นอกจากนี้ Flutter ยังรองรับฟีเจอร์ระดับเนทีฟ เช่น `HapticFeedback` ที่ให้การสั่นตอบรับเมื่อกดสวิตช์ สร้างความรู้สึกมั่นใจในการสั่งงานจริง

### ข้อ 3: หากต้องการนำแอปพลิเคชันนี้ไปเผยแพร่จริงบน Google Play Store หรือ Apple App Store ขั้นตอนความปลอดภัยที่ต้องปรับปรุงเพิ่มเติมมีอะไรบ้าง? (พิจารณาเรื่อง MQTTS / TLS พอร์ต 8883, การเข้ารหัส Token ยืนยันตัวตน, และการเก็บรักษา Credential)
* **คำตอบ:**
  * **1. การเข้ารหัสช่องทางการสื่อสารด้วย MQTTS / TLS (Port 8883):**
    ต้องเปลี่ยนจากการใช้ Plain MQTT (Port 1883) ซึ่งส่งข้อมูลเป็น Plaintext ไร้การเข้ารหัส มาเป็น MQTTS ผ่านโปรโตคอล TLS v1.3 (Port 8883) โดยนำใบรับรองดิจิทัล CA Certificate (`ca.crt`) บรรจุเข้าสู่ SecurityContext ของแอปพลิเคชัน เพื่อทำการเข้ารหัสข้อมูลทุกแพ็กเก็ต ป้องกันการถูกดักฟัง (Sniffing) หรือการถูกโจมตีแบบดัดแปลงข้อมูลกลางทาง (Man-in-the-Middle Attack)
  * **2. การยืนยันตัวตนและการกำหนดสิทธิ์ระดับหัวข้อ (Authentication & Topic ACL):**
    ยกเลิกการเปิด Broker แบบ Anonymous (`allow_anonymous false`) และบังคับให้ผู้ใช้งานต้องล็อกอินด้วย Username/Password หรือใช้ JWT (JSON Web Token) / API Key ที่ออกโดยระบบคลาวด์ พร้อมทั้งกำหนด Access Control List (ACL) ให้ชัดเจน เพื่อให้แอปของผู้ใช้แต่ละคนสามารถเข้าถึงและสั่งการได้เฉพาะ Node ID ที่ตนเองเป็นเจ้าของเท่านั้น
  * **3. การจัดเก็บข้อมูลความลับอย่างปลอดภัย (Secure Credential Storage):**
    ห้าม Hard-code ข้อมูลรหัสผ่านหรือ Private Key ลงในโค้ดของแอปพลิเคชันโดยตรง โดยจะต้องจัดเก็บข้อมูลที่มีความสำคัญไว้ในพื้นที่ปลอดภัยของระบบปฏิบัติการ เช่น การใช้ปลั๊กอิน `flutter_secure_storage` ซึ่งทำงานร่วมกับ Android Keystore บนระบบ Android และ iOS Keychain บนระบบ Apple เพื่อป้องกันการถูกแกะโค้ดหรือ Reverse Engineering ไฟล์ APK/IPA จากผู้ไม่ประสงค์ดี
