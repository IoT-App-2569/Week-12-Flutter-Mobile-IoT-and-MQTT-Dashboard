# ใบงานการทดลองที่ 12.1
## 4. คำถามท้ายการทดลอง (Review Questions)
1. เพราะเหตุใดเราจึงต้องสุ่มชื่อ `clientId` เช่นการใส่ Timestamp ต่อท้าย แทนที่จะตั้งชื่อแบบคงที่?

```text
**เพราะ Broker ใช้ `clientId` ระบุตัวตนของแต่ละการเชื่อมต่อ และอนุญาตให้ `clientId` หนึ่งชื่อเชื่อมต่อได้เพียงครั้งละหนึ่ง Session เท่านั้น**
 
- ตามมาตรฐาน MQTT หากมี Client ใหม่เชื่อมต่อเข้ามาด้วย `clientId` ที่ซ้ำกับ Client ที่กำลังเชื่อมต่ออยู่ Broker จะตัดการเชื่อมต่อของ Client เดิมทิ้งทันที (Session Takeover)
- ในห้องเรียนที่นักศึกษาหลายคนรันโค้ดเดียวกันไปยัง Broker เดียวกัน หรือเปิดแอปพร้อมกันหลายหน้าต่าง หากใช้ชื่อคงที่จะเกิดการแย่งกันเชื่อมต่อ และเตะกันหลุดตลอดเวลา
- โค้ดตั้งค่า `autoReconnect = true` ไว้ หาก `clientId` ซ้ำกัน Client ทั้งสองฝั่งจะพยายามเชื่อมต่อใหม่และเตะอีกฝ่ายหลุดวนซ้ำไม่สิ้นสุด (Reconnect Loop)
- การต่อท้ายด้วย `DateTime.now().millisecondsSinceEpoch` ทำให้ได้ชื่อที่ไม่ซ้ำกันในทุกครั้งที่กด Connect
```

2. หากหน้าจอ Flutter รันบนอุปกรณ์จริง (Physical Android Phone) เหตุใดการกรอก IP `127.0.0.1` จึงไม่สามารถเชื่อมต่อ Broker ได้? และต้องใช้ IP ใด?

```text
**เพราะ `127.0.0.1` คือ Loopback Address ที่หมายถึงตัวอุปกรณ์เอง บนโทรศัพท์จึงชี้กลับไปที่ตัวโทรศัพท์ ซึ่งไม่มี Broker ทำงานอยู่**
 
- เมื่อรันบน Windows Desktop แอปและ Broker อยู่ในเครื่องเดียวกัน `127.0.0.1` จึงใช้ได้ แต่บนโทรศัพท์ แอปจะพยายามเชื่อมต่อพอร์ต 1883 ของโทรศัพท์เอง และเกิด `SocketException` (Connection refused)
- ต้องใช้ **IPv4 Address วงแลนของคอมพิวเตอร์ที่รัน Broker** เช่น `192.168.1.100` ตรวจสอบได้ด้วยคำสั่ง `ipconfig` และโทรศัพท์ต้องเชื่อมต่อ Wi-Fi วงเดียวกับคอมพิวเตอร์
- Broker ต้องรันด้วยไฟล์คอนฟิกที่มี `listener 1883 0.0.0.0` และ `allow_anonymous true` เพราะการรัน `mosquitto -v -p 1883` ใน Mosquitto 2.x จะรับการเชื่อมต่อเฉพาะ `127.0.0.1` เท่านั้น
- Windows Defender Firewall ต้องอนุญาตการเชื่อมต่อขาเข้าพอร์ต TCP 1883 และหากใช้ Android Emulator ให้ใช้ IP พิเศษ `10.0.2.2` ซึ่งชี้ไปยัง Loopback ของคอมพิวเตอร์ที่รัน Emulator

```

3. การตั้งค่า `keepAlivePeriod` มีความจำเป็นอย่างไรในสภาพแวดล้อมเครือข่ายไร้สาย?

```text
**`keepAlivePeriod` ทำให้ทั้ง Client และ Broker ตรวจพบได้ว่าการเชื่อมต่อขาดหายไปแล้ว แม้จะไม่มีสัญญาณแจ้งการตัดการเชื่อมต่อใดๆ**
 
- เครือข่ายไร้สายหลุดได้ง่าย เช่น สัญญาณอ่อน เปลี่ยนจาก Wi-Fi เป็น 4G หรือโทรศัพท์เข้าโหมดประหยัดพลังงาน การเชื่อมต่อ TCP มักขาดไปโดยไม่มีการแจ้งปิด (Half-open Connection) ทำให้ทั้งสองฝั่งยังเข้าใจว่าเชื่อมต่ออยู่
- เมื่อไม่มีข้อมูลรับส่งภายในช่วงเวลาที่กำหนด (20 วินาทีในแล็บนี้) Client จะส่งแพ็กเก็ต `PINGREQ` และรอ `PINGRESP` จาก Broker หากไม่ได้รับคำตอบ Client จะรู้ว่าการเชื่อมต่อหลุด เรียก `onDisconnected` และเริ่ม `autoReconnect`
- ฝั่ง Broker หากไม่ได้รับแพ็กเก็ตใดจาก Client เกิน 1.5 เท่าของ Keep Alive (20 × 1.5 = 30 วินาที) จะตัดการเชื่อมต่อ และเผยแพร่ LWT `Client crashed` ไปที่ `iot/flutter/lwt` หากไม่มี Keep Alive ข้อความ LWT จะไม่ถูกส่งเลย
- การส่ง `PINGREQ` เป็นระยะยังช่วยรักษาการเชื่อมต่อไม่ให้ถูกเราเตอร์หรือเครือข่ายมือถือตัดทิ้ง เพราะอุปกรณ์ NAT มักปิดการเชื่อมต่อที่ไม่มีการใช้งานเป็นเวลานาน
```
