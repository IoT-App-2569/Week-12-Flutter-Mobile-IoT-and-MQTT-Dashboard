# ใบงานการทดลองที่ 12.2
## 4. สรุปผลและคำถามท้ายการทดลอง
1. ประโยชน์ของการรอสัญญาณ ACK จากหัวข้อ `iot/esp32/led_ack` แทนการเปลี่ยน UI ทันที (Optimistic Update) คืออะไร?

```text
**หน้าจอแสดงสถานะที่เกิดขึ้นจริงกับฮาร์ดแวร์ ไม่ใช่เพียงสถานะที่ผู้ใช้สั่ง**
 
- การส่งคำสั่งสำเร็จไม่ได้แปลว่าหลอดไฟเปลี่ยนสถานะจริง เพราะข้อความอาจสูญหาย บอร์ดอาจค้าง หรือการสั่ง GPIO อาจล้มเหลว หากเปลี่ยน UI ทันที หน้าจอจะแสดงว่าไฟเปิดทั้งที่ไฟยังดับอยู่
- โค้ดล็อกสวิตช์ระหว่างรอ ACK (`onChanged: _isWaitingAck ? null : _toggleLed`) ป้องกันผู้ใช้กดซ้ำรัวๆ จนส่งคำสั่งซ้อนกันและสถานะสับสน
- ข้อความ ACK ส่งถึงทุกแอปที่ Subscribe อยู่ หากมีผู้ใช้หลายคนหรือหลายเครื่อง ทุกหน้าจอจะเห็นสถานะเดียวกัน แม้คนอื่นเป็นผู้กดสั่ง
- สำคัญมากกับอุปกรณ์ที่เกี่ยวข้องกับความปลอดภัย เช่น กลอนประตู ฮีตเตอร์ หรือปั๊มน้ำ ซึ่งผู้ใช้ต้องรู้สถานะจริงอย่างแน่นอน
```

2. ทำไมเราจึงควรตั้งแฟล็ก Retain (`-r`) สำหรับหัวข้อสถานะ `iot/esp32/status`?

```text
**เพื่อให้แอปที่เปิดขึ้นมาหรือเชื่อมต่อใหม่ภายหลังทราบสถานะปัจจุบันของบอร์ดทันทีที่ Subscribe**
 
- ESP32 ส่งข้อความ `online` เพียงครั้งเดียวตอนเชื่อมต่อ Broker สำเร็จ หากไม่ใช้ Retain แอปที่เปิดภายหลังจะไม่ได้รับข้อความนี้เลย
- แอปเริ่มต้นด้วย `_isDeviceOnline = false` หากไม่ได้รับสถานะ Retained แอปจะเข้าใจว่าบอร์ดออฟไลน์ และไม่ยอมให้สั่งงาน แม้บอร์ดจะทำงานอยู่จริง
- เมื่อแอปหลุดจาก Broker แล้วเชื่อมต่อใหม่ `onConnected` จะ Subscribe อีกครั้ง และได้รับสถานะล่าสุดจาก Broker ทันที
- LWT `offline` ต้องตั้ง Retain ด้วยเช่นกัน เพื่อเขียนทับค่า `online` เดิม หากไม่ตั้ง ค่า `online` ที่ค้างอยู่จะทำให้แอปที่เปิดภายหลังเข้าใจผิดว่าบอร์ดที่ดับไปแล้วยังออนไลน์ และส่งคำสั่งไปโดยไม่มีผู้รับ
```
