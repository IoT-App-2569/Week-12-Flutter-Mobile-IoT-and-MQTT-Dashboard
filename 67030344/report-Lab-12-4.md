# ใบงานการทดลองที่ 12.4
## 4. สรุปผลและคำถามท้ายบทเรียน
1. เหตุใดการใช้ `IndexedStack` ใน `MainNavigationShell` จึงมีความสำคัญอย่างยิ่งสำหรับแอปพลิเคชัน IoT แบบ Multi-tab เมื่อเทียบกับการสลับวิดเจ็ตด้วย `body: _pages[_currentIndex]`?

```text
**`IndexedStack` เก็บทุกหน้าไว้ใน Widget Tree ตลอดเวลาและแสดงเพียงหน้าเดียว ทำให้สถานะและการเชื่อมต่อ MQTT ของทุกแท็บไม่ถูกทำลายเมื่อสลับแท็บ**
 
- หากใช้ `body: _pages[_currentIndex]` หน้าที่ไม่ได้แสดงจะถูกถอดออกจาก Widget Tree ทำให้ State ถูกทำลายและเรียก `dispose()` ซึ่งสั่ง `_client?.disconnect()` ตัดการเชื่อมต่อ MQTT ทันที
- เมื่อสลับกลับมา `initState()` จะเชื่อมต่อ Broker ใหม่ด้วย `clientId` ใหม่ทุกครั้ง เกิดความหน่วงระหว่างรอเชื่อมต่อ และค่าสถิติสูงสุด ต่ำสุด และกราฟประวัติ `_history` จะหายไปทั้งหมด
- ระหว่างที่หน้าไม่ได้แสดง ข้อมูล Telemetry และข้อความ ACK ที่ส่งมาจะสูญหาย เพราะไม่มี Client ใด Subscribe อยู่ เช่น สั่งเปิดไฟแล้วสลับแท็บทันที ข้อความ ACK จะไม่ถูกรับ
- `IndexedStack` ทำให้ทั้งสองหน้ายังรับข้อมูลอยู่เบื้องหลัง กราฟสะสมข้อมูลต่อเนื่อง และสถานะ Online/Offline ถูกต้องทันทีเมื่อสลับกลับมา

```

2. เมื่อเปรียบเทียบการพัฒนาด้วย Flutter ในสัปดาห์นี้ กับการเปิดหน้าเว็บ HTTP บนเบราว์เซอร์ในสัปดาห์ที่ 8-10 ข้อใดให้ประสบการณ์การใช้งาน (UX) และความเสถียรที่ดีกว่าเมื่อข้อมูลเซนเซอร์มาด้วยความถี่สูง? เพราะเหตุใด?

```text
**Flutter ร่วมกับ MQTT ให้ประสบการณ์และความเสถียรที่ดีกว่า เพราะข้อมูลถูกส่งมาหาแอปทันทีผ่านการเชื่อมต่อที่เปิดค้างไว้ แทนการให้เบราว์เซอร์คอยถามข้อมูลซ้ำๆ**
 
- **รูปแบบการสื่อสาร** HTTP เป็นแบบ Request-Response เบราว์เซอร์ต้องส่งคำขอซ้ำเป็นระยะ (Polling) หรือรีเฟรชหน้าเพื่อดูค่าใหม่ ข้อมูลที่เกิดขึ้นระหว่างรอบคำขอจึงไม่ถูกแสดง ส่วน MQTT เป็นแบบ Publish/Subscribe ที่ Broker ส่งข้อมูลมาหาแอปทันทีที่มีค่าใหม่ ผ่านการเชื่อมต่อ TCP เดียวที่เปิดค้างไว้
- **ภาระของเครือข่ายและบอร์ด** ทุกคำขอ HTTP มี Header ขนาดหลายร้อยไบต์ และ ESP32 ที่เป็น Web Server ต้องตอบคำขอของผู้ชมทุกคนเอง เมื่อข้อมูลถี่หรือผู้ชมหลายคน บอร์ดจะตอบไม่ทันจนหน้าเว็บค้างหรือหมดเวลา ส่วน MQTT มี Header เพียง 2 ไบต์ และบอร์ดส่งข้อมูลครั้งเดียวไปที่ Broker ไม่ว่าจะมีผู้ชมกี่คน
- **การแสดงผล** Flutter คอมไพล์เป็นแอป Native และวาดหน้าจอที่ 60–120 เฟรมต่อวินาที เข็มมาตรวัดและกราฟจึงเคลื่อนไหวลื่นไหลด้วย `TweenAnimationBuilder` ส่วนหน้าเว็บที่รีเฟรชหรือแทนที่เนื้อหาบ่อยๆ มักกระพริบและกระตุก
- **ความสามารถเพิ่มเติม** แอปเก็บสถานะไว้ได้ต่อเนื่อง รองรับ Haptic Feedback ทราบสถานะ Online/Offline ผ่าน LWT และใช้งานนอกวงแลนได้ผ่าน Broker โดยไม่ต้องเปิดพอร์ตของบอร์ดสู่อินเทอร์เน็ต

```

3. หากต้องการนำแอปพลิเคชันนี้ไปเผยแพร่จริงบน Google Play Store หรือ Apple App Store ขั้นตอนความปลอดภัยที่ต้องปรับปรุงเพิ่มเติมมีอะไรบ้าง? (พิจารณาเรื่อง MQTTS / TLS พอร์ต 8883, การเข้ารหัส Token ยืนยันตัวตน, และการเก็บรักษา Credential)

```text
**ต้องเข้ารหัสการสื่อสารทั้งหมด ยืนยันตัวตนผู้ใช้ทุกคนก่อนเข้าถึง Broker จำกัดสิทธิ์ตามอุปกรณ์ของแต่ละคน และไม่เก็บข้อมูลลับไว้ในตัวแอป**
 
- **MQTTS / TLS พอร์ต 8883** ปิดพอร์ต 1883 ที่ไม่เข้ารหัส แล้วเชื่อมต่อผ่าน TLS ด้วย `_client.secure = true` และตรวจสอบใบรับรองของ Broker ที่ออกโดย CA ที่เชื่อถือได้ ควรใช้ชื่อโดเมนแทน IP และพิจารณาทำ Certificate Pinning เพื่อป้องกัน Man-in-the-Middle ส่วนบอร์ด ESP32 ควรใช้ mTLS เหมือนแล็บ 11.3
- **Token ยืนยันตัวตน** ยกเลิก `allow_anonymous true` ให้ผู้ใช้ล็อกอินกับ Server ยืนยันตัวตนก่อน แล้วรับ Token อายุสั้น (เช่น JWT) มาใช้เชื่อมต่อ Broker แทนรหัสผ่านถาวร และกำหนด ACL ให้ผู้ใช้แต่ละคน Publish/Subscribe ได้เฉพาะ Topic ของอุปกรณ์ตัวเอง เช่น `iot/<user_id>/...` แทน Topic รวม `iot/esp32/...` ที่ทุกคนเข้าถึงได้
- **การเก็บรักษา Credential** ห้ามฝัง IP, Username, Password หรือ Key ไว้ในซอร์สโค้ด เพราะไฟล์ APK และ IPA ถอดรหัสได้ง่าย ให้เก็บ Token ด้วย `flutter_secure_storage` ซึ่งใช้ Android Keystore และ iOS Keychain และสร้างแอปด้วย `--obfuscate` เพื่อให้วิเคราะห์โค้ดย้อนกลับได้ยากขึ้น
- **โครงสร้างพื้นฐานและข้อกำหนดของ Store** ไม่เปิด Broker บนเครื่องคอมพิวเตอร์ในห้องทดลองสู่อินเทอร์เน็ตโดยตรง ใช้ Broker บน Server หรือบริการคลาวด์ที่มี Firewall และจำกัดอัตราการเชื่อมต่อ และต้องจัดทำนโยบายความเป็นส่วนตัว (Privacy Policy) และกรอกแบบฟอร์มการใช้ข้อมูลตามที่ Store กำหนด
```
