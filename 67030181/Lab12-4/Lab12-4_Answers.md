## สรุปสิ่งที่ทำในแล็บนี้
แล็บ 12.4 เป็นแล็บสุดท้ายของสัปดาห์นี้ เป็นการเอาชิ้นส่วนทั้งหมดมารวมกันเป็นแอปเดียวที่สมบูรณ์ โดยผมเอาหน้าจอควบคุมสวิตช์จาก Lab 12.2 และหน้าจอมาตรวัดแรงดันจาก Lab 12.3 มารวมไว้ในแอปเดียวกันผ่าน Navigation Bar ด้านล่าง โดยใช้เทคนิค `IndexedStack` เพื่อไม่ให้การเชื่อมต่อ MQTT หลุดเวลาสลับหน้าจอไปมา

ในแล็บนี้สามารถทดสอบได้ทั้งการต่อบอร์ด ESP32 จริงเข้ากับวงจร Potentiometer (GPIO 34) และหลอดไฟ LED (GPIO 2) หรือถ้าไม่มีบอร์ดก็สามารถรันสคริปต์ `mock_esp32.ps1` บน PowerShell เพื่อจำลองพฤติกรรมของฮาร์ดแวร์แทนได้ครับ

## ตารางบันทึกผลการทดสอบจริง (Verification Test Matrix)
ผมได้ทำการทดสอบระบบครบทั้ง 4 กรณีทดสอบวิกฤต บันทึกผลได้ดังนี้ครับ:

| ข้อทดสอบ | สิ่งที่ทำตอนทดสอบ | พฤติกรรมที่เห็นบนแอปพลิเคชัน | ผลการทดสอบ |
| :--- | :--- | :--- | :---: |
| **Test Case 1: Telemetry Monitoring** | รันสคริปต์ `mock_esp32.ps1` ส่งคลื่นไซน์ (หรือหมุน Potentiometer บนบอร์ดจริง) | เข็มบน Radial Gauge หมุนขึ้นลงตามค่าแรงดันอย่างนุ่มนวล ตัวเลข Raw ADC เปลี่ยนแปลงสัมพันธ์กัน และกราฟ Sparkline วาดเส้นคลื่นไหลต่อเนื่อง | **ผ่าน (Pass)** |
| **Test Case 2: Actuator Remote Control** | แตะสวิตช์เปิด-ปิดไฟบนหน้าจอแท็บที่สอง | ตัวเครื่องมีการสั่น Haptic Feedback ตอนแตะ และในหน้าต่าง PowerShell ขึ้นข้อความว่าได้รับคำสั่ง `{"led":"ON"}` ทันที | **ผ่าน (Pass)** |
| **Test Case 3: State Sync & Physical ACK** | ปล่อยให้สคริปต์/บอร์ดตอบกลับข้อความยืนยันสถานะกลับมา | พอแอปได้รับข้อความ `iot/esp32/led_ack` สวิตช์จะปลดล็อคแล้วเปลี่ยนเป็นเปิดค้างไว้ และไอคอนหลอดไฟเรืองแสงสีเขียวทันที ไม่เกิดปัญหาหน้าจอค้าง | **ผ่าน (Pass)** |
| **Test Case 4: Fault Tolerance (LWT)** | กด `Ctrl + C` ปิดสคริปต์จำลอง (หรือถอดสาย USB ของบอร์ด ESP32 ออก) | Broker ส่ง LWT `"offline"` มาที่แอปทันที ป้ายสถานะด้านบนเปลี่ยนเป็นสีแดงว่า `OFFLINE` และสวิตช์จะล็อคกดไม่ได้ ป้องกันการกดสั่งตอนบอร์ดดับ | **ผ่าน (Pass)** |

## ผลการวัดความเร็วการตอบสนอง (Control Latency Benchmark)
ผมลองจับเวลาตั้งแต่แตะสวิตช์ในแอป จนกระทั่งได้รับข้อความ ACK ตอบกลับมา (Round-Trip Time - RTT):

| สภาพแวดล้อมที่ทดสอบ | ลักษณะการเชื่อมต่อ | เวลาเฉลี่ย (RTT) | ข้อสังเกตจากที่ทดสอบจริง |
| :--- | :--- | :---: | :--- |
| **Wi-Fi วงเดียวกัน (LAN)** | คอมพิวเตอร์และมือถือต่อ Wi-Fi เดียวกันในห้อง | **ประมาณ 25 - 40 ms** | เร็วมากครับ พอกดปุ่มปุ๊บ หลอดไฟแทบจะติดพร้อมกับจังหวะที่มือสัมผัสจอเลย ไม่รู้สึกหน่วง |
| **ต่อผ่านเน็ตมือถือ 4G** | มือถือต่อเน็ตซิม 4G ยิงเข้ามาหา Broker | **ประมาณ 100 - 180 ms** | มีความดีเลย์ขึ้นมานิดหน่อยตามความแรงของสัญญาณเน็ต แต่ยังถือว่าไวมาก สวิตช์ตอบสนองได้ดีไม่สะดุด |

## คำตอบคำถามท้ายการทดลอง

### ข้อ 1: เหตุใดการใช้ `IndexedStack` ใน `MainNavigationShell` จึงมีความสำคัญอย่างยิ่งสำหรับแอปพลิเคชัน IoT แบบ Multi-tab เมื่อเทียบกับการสลับวิดเจ็ตด้วย `body: _pages[_currentIndex]`?
**ตอบ:**  
เรื่องนี้สำคัญมากเลยครับ เพราะถ้าเราเขียนแบบธรรมดาคือ `body: _pages[_currentIndex]` เวลาที่เรากดเปลี่ยนแท็บจากหน้าเกจวัดไปหน้าสวิตช์ ตัว Flutter มันจะทำลาย (Dispose) หน้าเกจวัดทิ้งออกจากหน่วยความจำทันที 

พอหน้าจอโดนทำลาย สิ่งที่พังตามไปด้วยคือ:
1. ท่อการเชื่อมต่อ MQTT Socket จะถูกตัดขาด ทำให้พอเรากดสลับแท็บกลับมา ตัวแอปต้องมานั่ง Connect และ Subscribe ใหม่อีกรอบ เสียเวลาและทำให้แอปกระตุก
2. ข้อมูลสถิติที่เราเก็บสะสมไว้ เช่น กราฟเส้น 30 จุดย้อนหลัง หรือค่า Max/Min จะหายเกลี้ยง กลายเป็นหน้าจอโล่งๆ เหมือนเพิ่งเปิดแอปใหม่

แต่ถ้าเราใช้ `IndexedStack` ตัว Flutter จะสร้างหน้าจอทั้งสองหน้าค้างไว้ในเมมโมรี่ตลอดเวลา แค่ซ่อนหน้าที่ไม่ได้ใช้อยู่ไว้ข้างหลัง ทำให้หน้าจอทั้งสองหน้ายังสามารถรับข้อมูลเซนเซอร์สดๆ จาก Broker อยู่เบื้องหลังได้ตลอดเวลา พอเรากดสลับแท็บปุ๊บ ข้อมูลก็อัปเดตพร้อมโชว์ทันทีแบบเรียลไทม์ 100% ไม่มีสะดุดเลยครับ

### ข้อ 2: เมื่อเปรียบเทียบการพัฒนาด้วย Flutter ในสัปดาห์นี้ กับการเปิดหน้าเว็บ HTTP บนเบราว์เซอร์ในสัปดาห์ที่ 8-10 ข้อใดให้ประสบการณ์การใช้งาน (UX) และความเสถียรที่ดีกว่าเมื่อข้อมูลเซนเซอร์มาด้วยความถี่สูง? เพราะเหตุใด?
**ตอบ:**  
**Flutter ร่วมกับ MQTT ดีกว่าแบบเห็นได้ชัดเจนเลยครับ** จากที่เคยทำมามีข้อเปรียบเทียบหลักๆ ดังนี้:
1. **เรื่องความเบาของข้อมูล (Overhead):** สัปดาห์ก่อนๆ ที่ทำ HTTP บนเว็บ เราต้องใช้วิธี Polling คือให้เว็บยิงขอดูข้อมูลซ้ำๆ ทุกครึ่งวินาที ซึ่งแต่ละครั้งที่ยิงจะมีก้อน Header ของ HTTP ติดไปด้วยหลายร้อยไบต์ ทำให้เปลืองเน็ตและบอร์ด ESP32 ทำงานหนักมาก แต่พอมาใช้ MQTT ในสัปดาห์นี้ มันเปิดท่อ TCP ค้างไว้แค่เส้นเดียว พอบอร์ดมีข้อมูลก็ดัน (Push) มาให้ทันที ตัว Header มีขนาดแค่ 2 ไบต์เท่านั้น ประหยัดกว่ากันเยอะมาก
2. **เรื่องความลื่นของหน้าจอ:** หน้าเว็บบนเบราว์เซอร์เวลาข้อมูลมาถี่ๆ จอจะเริ่มหน่วงและกระตุกเพราะต้องคอยแก้ DOM บนหน้าเว็บ แต่ Flutter มันคอมไพล์โค้ดเป็นรหัสเครื่องแล้วใช้เอนจินกราฟิกของมันเองวาดลงบนหน้าจอตรงๆ ทำให้ภาพลื่นระดับ 60 ถึง 120 FPS ไม่กระตุกเลย
3. **ฟีลลิ่งการใช้งาน (UX):** Flutter ทำงานเป็นแอปในมือถือจริงๆ มีระบบสั่นเตือน (Haptic Feedback) ตอนกดสวิตช์ มีแอนิเมชันเข็มที่นุ่มนวล และเวลาเน็ตหลุดมันก็ Reconnect ให้เองอัตโนมัติ ไม่ต้องคอยกด F5 รีเฟรชหน้าเว็บเหมือนตอนทำ HTTP ครับ

### ข้อ 3: หากต้องการนำแอปพลิเคชันนี้ไปเผยแพร่จริงบน Google Play Store หรือ Apple App Store ขั้นตอนความปลอดภัยที่ต้องปรับปรุงเพิ่มเติมมีอะไรบ้าง? (พิจารณาเรื่อง MQTTS / TLS พอร์ต 8883, การเข้ารหัส Token ยืนยันตัวตน, และการเก็บรักษา Credential)
**ตอบ:**  
ถ้าจะเอาขึ้น Store ให้คนทั่วไปใช้จริงๆ ต้องปรับเรื่องความปลอดภัยหลายจุดเลยครับ เพราะเวอร์ชันแล็บเราทำเพื่อทดสอบเลยยังไม่ได้ใส่ระบบรักษาความปลอดภัย:
1. **เปลี่ยนมาใช้ MQTTS / TLS (พอร์ต 8883):** ตอนนี้เราใช้พอร์ต 1883 ธรรมดา ข้อมูลทุกอย่างวิ่งเป็นตัวหนังสือธรรมดา ถ้ามีคนดักจับข้อมูลใน Wi-Fi ก็จะเห็นคำสั่งหมดเลย ถ้าจะขึ้น Store ต้องเปลี่ยนไปใช้พอร์ต 8883 ที่มีการเข้ารหัส SSL/TLS และต้องติดตั้งใบรับรอง (Digital Certificate) ที่ Broker ด้วย เพื่อป้องกันคนดักฟังหรือปลอมแปลงคำสั่ง
2. **ระบบล็อกอินและสิทธิ์ (Auth & ACL):** ต้องปิด `allow_anonymous` ทันที และทำระบบล็อกอิน เช่นใช้ Username/Password หรือใช้ระบบ Token (JWT) และต้องตั้งค่า ACL บน Broker ด้วยว่า ผู้ใช้คนนี้มีสิทธิ์สั่งเฉพาะอุปกรณ์ของตัวเองเท่านั้น ห้ามส่งคำสั่งข้ามไปเปิดปิดไฟบ้านคนอื่น
3. **การเก็บรหัสผ่านในเครื่องมือถือ:** ห้ามเขียนรหัสผ่านหรือ Secret Key แปะไว้ในโค้ด Dart เด็ดขาด เพราะมีคนแงะไฟล์ APK ออกมาดูได้ ควรใช้ไลบรารีอย่าง `flutter_secure_storage` เพื่อให้ระบบนำรหัสไปเก็บไว้ในตู้นิรภัยของเครื่องมือถือ (เช่น Android Keystore หรือ iOS Keychain)
4. **การทำ Code Obfuscation:** ก่อนจะแพ็กแอปส่งขึ้น Store ต้องสั่งบิ้วด์ด้วยคำสั่ง Obfuscate ของ Flutter เพื่อกวนโค้ดให้อ่านยาก ป้องกันไม่ให้แฮกเกอร์แกะไฟล์แอปพลิเคชันกลับมาเป็นซอร์สโค้ดต้นฉบับได้ครับ
