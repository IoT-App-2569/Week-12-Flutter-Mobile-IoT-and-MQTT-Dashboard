### ❓ ตอบคำถามท้ายการทดลอง
1. **เพราะเหตุใดเราจึงต้องสุ่มชื่อ clientId เช่นการใส่ Timestamp ต่อท้าย แทนที่จะตั้งชื่อแบบคงที่?**

   เพราะ MQTT Broker ใช้ค่า clientId ในการระบุตัวตนและจัดการสถานะการเชื่อมต่อของแต่ละไคลเอนต์ หากเราเขียนชื่อคงที่ไว้ในโค้ดแล้วเปิดรันแอปพร้อมกันหลายเครื่อง หรือเมื่อแอปหลุดการเชื่อมต่อแล้วพยายามต่อใหม่ทันที Broker จะมองว่ามีชื่อซ้ำและสั่งตัดการเชื่อมต่อเดิมออก (Disconnect) การนำค่า Timestamp มาต่อท้ายจึงช่วยให้ได้ชื่อใหม่ที่ไม่ซ้ำกันเลยในแต่ละครั้ง

2. **หากหน้าจอ Flutter รันบนอุปกรณ์จริง (Physical Android Phone) เหตุใดการกรอก IP 127.0.0.1 จึงไม่สามารถเชื่อมต่อ Broker ได้? และต้องใช้ IP ใด?**

   เนื่องจาก 127.0.0.1 คือไอพี Loopback ที่อ้างอิงถึงตัวเครื่องที่กำลังรันแอปพลิเคชันนั้นอยู่ เมื่อนำแอปไปรันบนมือถือ Android จริง เลข 127.0.0.1 จึงหมายถึงตัวโทรศัพท์เองซึ่งไม่ได้เปิดบริการ MQTT Broker ไว้ จึงเชื่อมต่อไม่ได้ ต้องแก้ไขโดยใช้หมายเลข IPv4 ของเครื่องคอมพิวเตอร์ที่รัน Mosquitto Broker ที่อยู่ในวง Wi-Fi เดียวกัน เช่น 192.168.1.112

3. **การตั้งค่า keepAlivePeriod มีความจำเป็นอย่างไรในสภาพแวดล้อมเครือข่ายไร้สาย?**

   ในระบบไร้สายอาจเกิดเหตุการณ์ที่สัญญาณหลุดหรืออุปกรณ์ดับไปโดยไม่มีการส่งแพ็กเก็ตแจ้งยกเลิกการเชื่อมต่อตามปกติ การกำหนดค่า keepAlivePeriod จะช่วยให้ไคลเอนต์ส่งแพ็กเก็ต PINGREQ ไปหา Broker ตามระยะเวลาที่กำหนดเพื่อแสดงว่ายังออนไลน์อยู่ หาก Broker ไม่ได้รับการติดต่อเกินเวลาที่กำหนดก็จะตัดสินว่าอุปกรณ์ออฟไลน์และปล่อยข้อความ LWT แจ้งเตือนระบบทันที

### ❓ ตอบคำถามท้ายการทดลอง
1. **ประโยชน์ของการรอสัญญาณ ACK จากหัวข้อ iot/esp32/led_ack แทนการเปลี่ยน UI ทันที (Optimistic Update) คืออะไร?**

   ช่วยให้ผู้ใช้งานมั่นใจได้ว่าสถานะไฟที่แสดงบนหน้าจอตรงกับสถานะของหลอดไฟจริงบนบอร์ด ESP32 เสมอ เพราะแอปจะรอจนกว่าบอร์ดจะประมวลผลคำสั่งและส่งข้อความยืนยันกลับมาที่หัวข้อ iot/esp32/led_ack ก่อนจึงค่อยเปลี่ยนสถานะสวิตช์ หากเปลี่ยน UI ทันทีที่กดโดยไม่รอ ACK เมื่อเกิดปัญหาเครือข่ายขัดข้องหน้าจอจะแสดงสถานะผิดพลาดไม่ตรงกับความจริง

2. **ทำไมเราจึงควรตั้งแฟล็ก Retain (-r) สำหรับหัวข้อสถานะ iot/esp32/status?**

   การใส่แฟล็ก Retain (-r) บนหัวข้อ iot/esp32/status ทำให้ Broker จดจำข้อความสถานะล่าสุดของบอร์ดเอาไว้ตลอดเวลา ประโยชน์คือเมื่อมีแอปพลิเคชันเปิดเข้ามาเชื่อมต่อทีหลังและกด Subscribe หัวข้อนี้ ก็จะได้รับข้อความสถานะล่าสุดทันทีโดยไม่ต้องรอให้บอร์ดส่งสถานะรอบใหม่เข้ามา

### ❓ ตอบคำถามท้ายการทดลอง
1. **เหตุใดการใช้ TweenAnimationBuilder จึงทำให้เข็มมาตรวัดดูนุ่มนวลและไม่กระตุก แม้ข้อมูลเซนเซอร์จะเข้ามาทุกๆ 500 มิลลิวินาที?**

   เพราะ TweenAnimationBuilder ทำหน้าที่คำนวณค่าตัวเลขระหว่างจุดเริ่มต้นและจุดสิ้นสุดให้เปลี่ยนแปลงอย่างต่อเนื่องตลอดช่วงเวลา 300 ms ด้วยรูปแบบความเร่ง Curves.easeOutCubic แม้ว่าข้อมูลจริงจาก MQTT จะส่งเข้ามาห่างกันทุก 500 ms แต่วิดเจ็ตจะช่วยเรนเดอร์เฟรมย่อยๆ ให้สอดคล้องกับอัตรารีเฟรชหน้าจอ 60 FPS จึงทำให้การเคลื่อนที่ของมาตรวัดดูสมูทไม่กระโดด

   การจำกัดขนาดของ _history ให้เก็บข้อมูลไม่เกิน 30 ตัวอย่างโดยลบค่าเก่าสุดออกเมื่อมีค่าใหม่เข้ามา ช่วยให้การใช้หน่วยความจำของสมาร์ตโฟนคงที่และไม่เพิ่มขึ้นเรื่อยๆ ตามระยะเวลาที่เปิดแอป อีกทั้งยังลดภาระของ CPU/GPU ในการวาดเส้นกราฟของ CustomPainter ให้ทำงานได้รวดเร็วคงที่ทุกเฟรม

3. **หากเซนเซอร์ส่งค่าผิดพลาด เช่น ค่านอกช่วง 0 - 3.3V หรือค่าเป็น null โค้ดส่วนใดใน telemetry_dashboard_screen.dart ที่ช่วยป้องกันไม่ให้แอปแครช?**

   ในไฟล์ telemetry_dashboard_screen.dart มีการป้องกันไว้ 2 จุดหลัก คือ 1) การครอบโค้ดแปลงข้อมูล JSON ด้วย try-catch พร้อมใช้ตัวดำเนินการตรวจสอบค่าว่าง (data['voltage'] as num?)?.toDouble() ?? 0.0 เพื่อป้องกันข้อผิดพลาดเมื่อค่าเป็น null และ 2) การใช้คำสั่ง .clamp(0.0, 1.0) ในคลาสวาดกราฟและมาตรวัดเพื่อจำกัดสัดส่วนค่าแรงดันไม่ให้เกินช่วง 0.0 ถึง 1.0 แม้ว่าเซนเซอร์จะส่งค่าผิดปกติที่อยู่นอกช่วง 0 - 3.3V มา

### ❓ ตอบคำถามท้ายการทดลอง
1. **เหตุใดการใช้ IndexedStack ใน MainNavigationShell จึงมีความสำคัญอย่างยิ่งสำหรับแอปพลิเคชัน IoT แบบ Multi-tab เมื่อเทียบกับการสลับวิดเจ็ตด้วย body: _pages[_currentIndex]?**

   การใช้ IndexedStack ช่วยให้หน้าจอทั้งสองแท็บยังคงถูกสร้างและรักษาสถานะ (State) อยู่ในหน่วยความจำตลอดเวลาแม้จะถูกซ่อนไว้เมื่อสลับไปอีกแท็บหนึ่ง ทำให้การเชื่อมต่อ MQTT และข้อมูลกราฟย้อนหลังยังคงทำงานต่อเนื่องไม่สะดุด ต่างจากการใช้ body: _pages[_currentIndex] ที่จะทำลายวิดเจ็ตหน้าเดิมทิ้งทุกครั้งที่สลับหน้า ทำให้ต้องเชื่อมต่อ Broker ใหม่ตลอดเวลา

2. **เมื่อเปรียบเทียบการพัฒนาด้วย Flutter ในสัปดาห์นี้ กับการเปิดหน้าเว็บ HTTP บนเบราว์เซอร์ในสัปดาห์ที่ 8-10 ข้อใดให้ประสบการณ์การใช้งาน (UX) และความเสถียรที่ดีกว่าเมื่อข้อมูลเซนเซอร์มาด้วยความถี่สูง? เพราะเหตุใด?**

   แอปพลิเคชัน Flutter ที่รับส่งข้อมูลผ่าน MQTT ให้ประสบการณ์ใช้งานและความเสถียรที่ดีกว่าการเปิดหน้าเว็บ HTTP ในสัปดาห์ที่ 8-10 อย่างเห็นได้ชัด เพราะ MQTT ใช้การเชื่อมต่อ TCP ค้างไว้และส่งเฉพาะข้อมูลขนาดเล็กเมื่อมีอีเวนต์เกิดขึ้น ร่วมกับการวาดกราฟิกด้วยเอนจินของ Flutter ที่มีความลื่นไหลสูง ในขณะที่ HTTP มี Overhead ของ Header สูงและต้องคอยสร้างคำขอใหม่ซ้ำๆ ทำให้เกิดอาการหน่วงเมื่อรับข้อมูลความถี่สูง

3. **หากต้องการนำแอปพลิเคชันนี้ไปเผยแพร่จริงบน Google Play Store หรือ Apple App Store ขั้นตอนความปลอดภัยที่ต้องปรับปรุงเพิ่มเติมมีอะไรบ้าง? (พิจารณาเรื่อง MQTTS / TLS พอร์ต 8883, การเข้ารหัส Token ยืนยันตัวตน, และการเก็บรักษา Credential)**

   สำหรับการนำไปใช้งานจริงบน Store ต้องเพิ่มความปลอดภัย 3 ส่วนสำคัญ คือ 1) เปลี่ยนไปใช้ MQTTS ที่เข้ารหัสด้วย TLS บนพอร์ต 8883 เพื่อป้องกันการดักจับข้อมูลในเครือข่ายสาธารณะ 2) ตั้งค่าระบบยืนยันตัวตนด้วย Username/Password หรือ Token พร้อมกำหนดสิทธิ์การเข้าถึงแต่ละ Topic (ACL) บนฝั่ง Broker และ 3) จัดเก็บข้อมูลรหัสผ่านหรือ Token ไว้ในพื้นที่ปลอดภัยของอุปกรณ์ผ่านไลบรารี flutter_secure_storage แทนการฝังไว้ในซอร์สโค้ด

## 3. สรุปผลและการประยุกต์ใช้งาน

การปฏิบัติการในสัปดาห์ที่ 12 ทั้ง 4 ใบงานช่วยให้เข้าใจการพัฒนาแอปพลิเคชันมือถือด้วย Flutter เพื่อควบคุมและติดตามสถานะของบอร์ด ESP32 ผ่านโปรโตคอล MQTT ได้อย่างครบถ้วน เริ่มตั้งแต่การสร้างการเชื่อมต่อและการตั้งค่า Client ID แบบสุ่มเวลาใน Lab 12.1 การส่งคำสั่งเปิด-ปิดไฟพร้อมรับข้อความยืนยัน ACK และการใช้ Retained Message ใน Lab 12.2 การแสดงผลค่าแรงดันแบบเรียลไทม์ด้วย Radial Gauge และกราฟเส้นใน Lab 12.3 ไปจนถึงการรวมทุกหน้าจอด้วย IndexedStack และทดสอบการแจ้งเตือนบอร์ดดับด้วย LWT ใน Lab 12.4 ปัญหาที่พบระหว่างการทดลองคือการกำหนด IP ของ Broker ให้ตรงกับเครือข่ายที่ใช้ ซึ่งแก้ไขได้ด้วยการตรวจสอบ IPv4 ของเครื่องคอมพิวเตอร์ก่อนทดสอบ และสามารถนำความรู้ที่ได้ไปต่อยอดสร้างระบบ IoT สำหรับงานควบคุมอัตโนมัติได้จริง
