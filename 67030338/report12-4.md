## 4. สรุปผลและคำถามท้ายบทเรียน (Review Questions)

### ข้อ 1: เหตุใดการใช้ `IndexedStack` ใน `MainNavigationShell` จึงมีความสำคัญอย่างยิ่งสำหรับแอปพลิเคชัน IoT แบบ Multi-tab เมื่อเทียบกับการสลับวิดเจ็ตด้วย `body: _pages[_currentIndex]`?
* **คำตอบ:**
  * **การรักษาชีวิตของ State และการเชื่อมต่อ TCP/MQTT (State & Connection Persistence):** หากใช้ `_pages[_currentIndex]` ทุกครั้งที่ผู้ใช้สลับแท็บไปมา Flutter จะสั่งทำลาย (`dispose()`) วิดเจ็ตหน้าเดิมและสร้างใหม่ (`initState()`) เมื่อสลับกลับมา ส่งผลให้การเชื่อมต่อ `MqttServerClient` ถูกตัดและต้องเชื่อมต่อใหม่ซ้ำๆ ทุกครั้งที่เปลี่ยนหน้า
  * **การรักษาข้อมูลประวัติเรียลไทม์ (Continuous Data Buffering):** `IndexedStack` จะคงวิดเจ็ตลูกทุกหน้าไว้ในหน่วยความจำพร้อมกันแต่เลือกแสดงผลเฉพาะหน้าที่ตรงกับ `index` ทำให้หน้า `TelemetryDashboardScreen` ยังคงรับข้อมูลเซนเซอร์และสะสมอาร์เรย์ `_history` (กราฟ 30 จุดย้อนหลัง รวมถึงค่า Max/Min) อยู่เบื้องหลังอย่างต่อเนื่องแม้ผู้ใช้อยู่ที่แท็บ `ActuatorControlScreen`

### ข้อ 2: เมื่อเปรียบเทียบการพัฒนาด้วย Flutter ในสัปดาห์นี้ กับการเปิดหน้าเว็บ HTTP บนเบราว์เซอร์ในสัปดาห์ที่ 8-10 ข้อใดให้ประสบการณ์การใช้งาน (UX) และความเสถียรที่ดีกว่าเมื่อข้อมูลเซนเซอร์มาด้วยความถี่สูง? เพราะเหตุใด?
* **คำตอบ:**
  * **แอปพลิเคชัน Flutter ร่วมกับ MQTT ให้ UX และความเสถียรที่ดีกว่าอย่างชัดเจน** ด้วยเหตุผลดังนี้:
    1. **สถาปัตยกรรมการสื่อสาร (Persistent Pub/Sub vs HTTP Request/Response):** MQTT ใช้การเชื่อมต่อ TCP ค้างไว้เพียงครั้งเดียวและส่งเฉพาะเฟรมข้อมูลขนาดเล็ก (Header เพียง 2 ไบต์) แบบ Event-Driven ทันทีที่มีข้อมูลใหม่ ในขณะที่ HTTP แบบดั้งเดิมมี Overhead ของ Header สูงและหากใช้การดึงข้อมูลซ้ำๆ (HTTP Polling) ที่ความถี่สูง (เช่น ทุก 500ms) จะทำให้ ESP32 รับภาระหนักจนเกิดความหน่วงหรือค้างได้ง่าย
    2. **ประสิทธิภาพการวาดกราฟิก (Hardware-Accelerated Rendering Engine):** Flutter คอมไพล์เป็น Native Machine Code และวาด UI ผ่านเอนจินกราฟิก (Impeller/Skia) บน GPU โดยตรงด้วยความเร็ว 60–120 FPS ร่วมกับ `CustomPainter` และ `TweenAnimationBuilder` จึงแสดงผลเข็มมาตรวัดและกราฟเส้นได้ลื่นไหลกว่าการอัปเดต DOM บนเว็บเบราว์เซอร์ พร้อมรองรับ Native API เช่น `HapticFeedback`

### ข้อ 3: หากต้องการนำแอปพลิเคชันนี้ไปเผยแพร่จริงบน Google Play Store หรือ Apple App Store ขั้นตอนความปลอดภัยที่ต้องปรับปรุงเพิ่มเติมมีอะไรบ้าง? (พิจารณาเรื่อง MQTTS / TLS พอร์ต 8883, การเข้ารหัส Token ยืนยันตัวตน, และการเก็บรักษา Credential)
* **คำตอบ:**
  * **1. การเข้ารหัสช่องทางสื่อสารด้วย MQTTS / TLS (Port 8883):**
    * เปลี่ยนจากการส่งข้อมูลแบบ Plaintext บนพอร์ต `1883` ไปใช้พอร์ต `8883` (`client.secure = true` และกำหนด `SecurityContext`) เพื่อเข้ารหัสข้อมูลด้วย TLS/SSL ป้องกันการดักฟังข้อมูลเซนเซอร์หรือการปลอมแปลงคำสั่งควบคุม (Man-in-the-Middle Attack)
  * **2. การยืนยันตัวตนและกำหนดสิทธิ์ (Authentication & Topic ACL):**
    * ปิดการเชื่อมต่อแบบ `allow_anonymous true` บน Broker และบังคับให้ใช้ Username/Password, JWT (JSON Web Token) หรือ Client Certificate (mTLS) พร้อมตั้งค่า Access Control List (ACL) จำกัดสิทธิ์ให้แต่ละอุปกรณ์ Publish/Subscribe ได้เฉพาะ Topic ของตนเองเท่านั้น
  * **3. การจัดเก็บข้อมูลความลับอย่างปลอดภัย (Secure Credential Storage):**
    * ห้ามฝัง (Hardcode) รหัสผ่าน, Token หรือ IP/Key ไว้ในซอร์สโค้ด Dart โดยตรง เพราะสามารถถูกถอดรหัสย้อนกลับ (Reverse Engineering) จากไฟล์ APK/IPA ได้ ต้องจัดเก็บ Token ไว้ในพื้นที่นิรภัยของระบบปฏิบัติการผ่านแพ็กเกจเช่น `flutter_secure_storage` (ซึ่งใช้ Android Keystore และ iOS Keychain)
