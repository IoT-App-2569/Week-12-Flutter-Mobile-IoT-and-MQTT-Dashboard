#### ทดสอบส่งข้อความสองทาง
* บนหน้าจอ Flutter: กรอก IP เป็น **`127.0.0.1`** (หรือ IP ของ Broker ที่เปิดรับ) แล้วกดปุ่ม **Connect**
* เมื่อสถานะเปลี่ยนเป็นสีเขียว ให้กดปุ่ม **Publish Test Message**
* สังเกตหน้าต่าง PowerShell `mosquitto_sub` ว่าได้รับข้อความ Ping หรือไม่
* ในอีกหน้าต่าง PowerShell ส่งข้อความตอบกลับไปยังหัวข้อที่ Flutter รอฟัง:
```powershell
mosquitto_pub -h 127.0.0.1 -p 1883 -t "test/broker/echo" -m "Echo response from CLI"
```

## 4. คำถามท้ายการทดลอง (Review Questions)
1. เพราะเหตุใดเราจึงต้องสุ่มชื่อ `clientId` เช่นการใส่ Timestamp ต่อท้าย แทนที่จะตั้งชื่อแบบคงที่?
   
    **ตอบ** ตามข้อกำหนดของมาตรฐาน MQTT Broker จะอนุญาตให้มี Client ID หนึ่งชื่อต่อหนึ่งเซสชันการเชื่อมต่อเท่านั้น หากมีอุปกรณ์หรือไคลเอนต์ตัวใหม่เชื่อมต่อเข้ามาด้วย Client ID ที่ซ้ำกับตัวเดิม Broker จะสั่งตัดการเชื่อมต่อ (Disconnect) ไคลเอนต์ตัวเก่าออกทันที การต่อท้ายด้วย Timestamp (DateTime.now().millisecondsSinceEpoch) จึงช่วยรับประกันว่า Client ID จะไม่ซ้ำกัน และป้องกันปัญหาการถูกแย่ง Connection สลับกันหลุดไปมา

3. หากหน้าจอ Flutter รันบนอุปกรณ์จริง (Physical Android Phone) เหตุใดการกรอก IP `127.0.0.1` จึงไม่สามารถเชื่อมต่อ Broker ได้? และต้องใช้ IP ใด?

   **ตอบ** เพราะ IP 127.0.0.1 คือ Local Loopback Address ซึ่งหากรันบนมือถือจริง จะหมายถึงตัวฮาร์ดแวร์ของโทรศัพท์เอง ไม่ใช่คอมพิวเตอร์ที่ Mosquitto Broker ทำงานอยู่ วิธีแก้ไขคือต้องเชื่อมต่อมือถือและคอมพิวเตอร์ให้อยู่บนวง LAN (Wi-Fi) เดียวกัน แล้วกรอกเป็น IPv4 Address ของเครื่องคอมพิวเตอร์ (เช่น 192.168.x.x ที่ตรวจสอบผ่านคำสั่ง ipconfig) พร้อมทั้งตั้งค่าไฟล์คอนฟิกของ Mosquitto ให้เปิดรับ listener 1883 0.0.0.0 และ allow_anonymous true

5. การตั้งค่า `keepAlivePeriod` มีความจำเป็นอย่างไรในสภาพแวดล้อมเครือข่ายไร้สาย?
   **ตอบ** ค่า keepAlivePeriod จะกำหนดให้ไคลเอนต์ส่งแพ็กเก็ต PINGREQ ไปยัง Broker ตามช่วงเวลาที่กำหนด หาก Broker ไม่ตอบ PINGRESP กลับมาตามเงื่อนไข ทั้งสองฝั่งจะรับรู้ได้ทันทีว่าการเชื่อมต่อหลุด และฝั่ง Flutter จะสามารถเริ่มกระบวนการ Reconnect ใหม่อัตโนมัติ (autoReconnect = true) ได้ทันทีโดยไม่ค้างสถานะหลอกไว้
