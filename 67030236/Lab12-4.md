### กิจกรรมที่ 12-4.4: การวัดความหน่วงเวลาในการควบคุม (Control Latency Benchmark)

1. วัดเวลาตั้งแต่แตะสวิตช์ในแอป จนกระทั่งได้รับข้อความยืนยัน `iot/esp32/led_ack` กลับมายังสมาร์ตโฟน (Round-Trip Time - RTT)
2. สังเกตความหน่วงและบันทึกผลเปรียบเทียบในตาราง:

| สภาพแวดล้อมเครือข่าย | ประเภทการเชื่อมต่อ | เวลาตอบสนองโดยเฉลี่ย (RTT: ms) | ความเสถียร / ข้อสังเกต |
| :--- | :--- | :--- | :--- |
| **Local Wi-Fi LAN** | สมาร์ตโฟนและบอร์ด ESP32 ต่อเข้ากับ Wi-Fi Router เดียวกันในห้องทดลอง | ประมาณ 20 – 60 ms | รวดเร็ว ตอบสนองแทบจะทันที |
| **Mobile Hotspot / 4G** | สมาร์ตโฟนเชื่อมต่อ 4G/5G ชี้มายัง Broker ผ่าน Public IP หรือ Tailscale/VPN | ประมาณ 80 – 250 ms | ขึ้นอยู่กับความแรงสัญญาณและ Routing |

## 4. สรุปผลและคำถามท้ายบทเรียน
1. เหตุใดการใช้ `IndexedStack` ใน `MainNavigationShell` จึงมีความสำคัญอย่างยิ่งสำหรับแอปพลิเคชัน IoT แบบ Multi-tab เมื่อเทียบกับการสลับวิดเจ็ตด้วย `body: _pages[_currentIndex]`?
```text
การใช้ IndexedStack มีความสำคัญอย่างยิ่งสำหรับแอปพลิเคชัน IoT เพราะช่วย รักษา State ของแต่ละแท็บไว้ในหน่วยความจำโดยไม่ทำลายทิ้ง (Preserve State):
1.ไม่ตัดท่อการเชื่อมต่อหรือข้อมูลเซนเซอร์ (Preserve Stream & Connection): หากใช้ body: _pages[_currentIndex] ทุกครั้งที่สลับแท็บ วิดเจ็ตหน้าเดิมจะถูกทำลายทิ้ง (dispose()) ทำให้ StreamSubscription, ตัวจับเวลา (Timer) หรือ State ในการดึงข้อมูล telemetry ดับไปด้วย พอสลับกลับมาต้องต่อใหม่และสร้างหน้าใหม่ตั้งแต่ต้น
2.รักษาประวัติข้อมูลและตำแหน่งบนหน้าจอ (No UI Flicker / Reset): ประวัติกราฟเซนเซอร์ในอาร์เรย์ (เช่น _history), สถานะปุ่มควบคุม และตำแหน่งการเลื่อนหน้าจอ (Scroll position) จะยังคงอยู่ครบถ้วน สลับแท็บไปมาได้ทันทีอย่างลื่นไหลโดยข้อมูลไม่รีเซ็ตเป็นค่าเริ่มต้น
```
2. เมื่อเปรียบเทียบการพัฒนาด้วย Flutter ในสัปดาห์นี้ กับการเปิดหน้าเว็บ HTTP บนเบราว์เซอร์ในสัปดาห์ที่ 8-10 ข้อใดให้ประสบการณ์การใช้งาน (UX) และความเสถียรที่ดีกว่าเมื่อข้อมูลเซนเซอร์มาด้วยความถี่สูง? เพราะเหตุใด?
```text
- โปรโตคอลและการจัดการทราฟฟิก (MQTT/Socket vs. HTTP Polling): หน้าเว็บ HTTP ทั่วไปมักใช้การ Polling หรือ Request/Response ซึ่งสร้างภาระ Overhead สูงจาก HTTP Headers ในทุกคำขอ หากส่งข้อมูลถี่ (เช่น ทุก 500 ms) จะทำให้เกิด Traffic แออัดและการตอบสนองล่าช้า ขณะที่ Flutter เชื่อมต่อผ่านท่อเดียวแบบ Real-time (เช่น MQTT) ที่มีขนาด Packet เล็กมาก จึงส่งข้อมูลต่อเนื่องได้เบาและเสถียรกว่า

- ประสิทธิภาพการเรนเดอร์ (Skia/Impeller vs. DOM Manipulation): Flutter วาดกราฟิกและ UI ลงบน Canvas ด้วยเอนจินของตัวเองโดยตรงที่ 60/120 FPS จึงทำแอนิเมชัน (เช่น TweenAnimationBuilder) และอัปเดตกราฟเซนเซอร์ความถี่สูงได้ลื่นไหล ไม่เกิดอาการหน่วงหรือภาพกระตุกเหมือนหน้าเว็บที่ต้องคอยคำนวณและวาด DOM ใหม่ซ้ำๆ

- การจัดการหน่วยความจำและการตอบสนองของ UI: Flutter รันเป็นเนทีฟโค้ดและควบคุม Memory Buffer ได้อย่างมีประสิทธิภาพ (เช่น การใช้ Circular/Fixed-size buffer) ทำให้แอปคงความลื่นไหล ตอบสนองต่อการสัมผัสได้ทันที ไม่เกิดอาการค้างหรือกินทรัพยากรเบราว์เซอร์จนหน้าเว็บโหลดช้าลงเรื่อยๆ
```
3. หากต้องการนำแอปพลิเคชันนี้ไปเผยแพร่จริงบน Google Play Store หรือ Apple App Store ขั้นตอนความปลอดภัยที่ต้องปรับปรุงเพิ่มเติมมีอะไรบ้าง? (พิจารณาเรื่อง MQTTS / TLS พอร์ต 8883, การเข้ารหัส Token ยืนยันตัวตน, และการเก็บรักษา Credential)
```text
เปลี่ยนไปใช้ MQTTS (พอร์ต 8883), ล็อกเก็บบัญชีผู้ใช้ด้วย flutter_secure_storage (Keystore/Keychain), และใช้ JWT/ACL กำหนดสิทธิ์แทนการฝังรหัสผ่านลงในโค้ดครับ
```
