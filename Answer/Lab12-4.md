## 6. คำถามท้ายบทเรียน

### ข้อ 1. ทำไม `IndexedStack` สำคัญกว่าการใช้ `body: _pages[_currentIndex]`?

- **`_pages[_currentIndex]`:** เมื่อสลับแท็บ วิดเจ็ตหน้าเดิมจะถูกถอดออกจาก Widget Tree ทำให้ `State` ถูก `dispose()` ซึ่งในโค้ดนี้คือการเรียก `_client?.disconnect()` เมื่อกลับมาหน้าเดิม `initState()` จะเชื่อมต่อ MQTT ใหม่และค่าทั้งหมดหาย (กราฟ 30 จุด, Max/Min, สถานะ LED) ระหว่างที่อยู่อีกหน้ายังพลาดข้อความ Telemetry และ ACK อีกด้วย
- **`IndexedStack`:** สร้างทุกหน้าไว้พร้อมกันแต่แสดงทีละหน้า หน้าที่ซ่อนอยู่**ยังมีชีวิต** State และการเชื่อมต่อ MQTT จึงทำงานต่อเนื่อง กราฟยังสะสมข้อมูลเบื้องหลัง และสลับแท็บได้ทันทีโดยไม่ต้อง Connect หรือ Subscribe ใหม่
- สำหรับแอป IoT ซึ่งเป็นแอปที่ “ต้องฟังตลอดเวลา” ข้อนี้สำคัญมาก แลกกับการใช้หน่วยความจำและการเชื่อมต่อเพิ่มเล็กน้อย (โค้ดปัจจุบันเปิด 2 Client แยกกัน หากต้องการปรับให้ดีขึ้นควรรวมเป็น MQTT Service ตัวเดียว)

### ข้อ 2. Flutter (สัปดาห์นี้) เทียบกับหน้าเว็บ HTTP (สัปดาห์ 8–10) แบบไหนดีกว่าเมื่อข้อมูลมาถี่?

**Flutter + MQTT ดีกว่า** ด้วยเหตุผลดังนี้

| ประเด็น | หน้าเว็บ HTTP (Polling) | Flutter + MQTT |
| :--- | :--- | :--- |
| รูปแบบการรับข้อมูล | Pull: Browser ต้องถามซ้ำทุกช่วงเวลา | Push: Broker ส่งให้ทันทีที่มีข้อมูล |
| Overhead ต่อข้อความ | HTTP Header หลายร้อยไบต์ต่อ Request และอาจเปิด TCP ใหม่ทุกครั้ง | Header MQTT 2 ไบต์บน TCP ที่เปิดค้างไว้ |
| ความหน่วง | ไม่ต่ำกว่าช่วง Polling + เวลา Request | ประมาณเท่าเวลาเดินทางของเครือข่าย (20–60 ms ใน LAN) |
| ภาระของ ESP32 | ต้องรัน Web Server ตอบทุก Request ซึ่งหนักเมื่อมีผู้ใช้หลายคน | Publish ครั้งเดียว Broker กระจายต่อให้ทุก Client |
| การแสดงผล | DOM Update + JavaScript อาจกระตุก | Render ด้วย Engine ของ Flutter โดยตรง แอนิเมชันลื่น 60 fps |
| สถานะออนไลน์ | ต้องรอให้ Request Timeout | LWT + Retain รู้สถานะทันที |
| ฟีเจอร์มือถือ | จำกัด | Haptic Feedback, ทำงานเบื้องหลัง, ทำต่อเป็น Push Notification ได้ |

ข้อดีที่เหลืออยู่ของหน้าเว็บคือไม่ต้องติดตั้งแอป และเปิดจากเบราว์เซอร์ไหนก็ได้

### ข้อ 3. ถ้าจะเผยแพร่บน Google Play / App Store ต้องปรับปรุงความปลอดภัยอะไรบ้าง?

1. **เข้ารหัสการสื่อสารด้วย MQTTS (TLS) พอร์ต 8883** หรือ WSS 443 แทน 1883 ที่เป็นข้อความเปล่า ตั้ง `client.secure = true` ใน Flutter และใช้ `mqtts://` กับ CA Certificate บน ESP32 ควรทำ Certificate Pinning เพื่อกัน Man-in-the-Middle
2. **ปิด `allow_anonymous`:** ให้ทุก Client ยืนยันตัวตนด้วย Username/Password, JWT Token อายุสั้น หรือ X.509 Client Certificate (เหมาะกับ ESP32 แต่ละตัว)
3. **ACL จำกัดสิทธิ์ราย Topic:** ผู้ใช้แต่ละคนเห็นเฉพาะ `iot/<deviceId>/...` ของตัวเอง และ ESP32 ห้าม Subscribe Topic ของอุปกรณ์อื่น
4. **เก็บ Credential อย่างปลอดภัย:** บนมือถือใช้ `flutter_secure_storage` (Android Keystore / iOS Keychain) ไม่ฝังรหัสไว้ในโค้ดเพราะ APK แกะดูได้ บน ESP32 ไม่ Hard-code รหัส Wi-Fi/MQTT ใน `main.c` ให้ใช้ Wi-Fi Provisioning + NVS Encryption + Flash Encryption + Secure Boot
5. **ตรวจสอบ Input ฝั่งบอร์ด:** เช่นจำกัดขนาด Payload (ตอนนี้ใช้ buffer 128 ไบต์) และ Rate Limit คำสั่ง
6. **ไม่เปิด Broker ออกอินเทอร์เน็ตตรง ๆ:** ใช้ Managed Broker (เช่น AWS IoT Core, HiveMQ Cloud, EMQX) หรือ VPN/Tailscale พร้อม Firewall
7. **ด้าน Store:** มี Privacy Policy, ขอ Permission เท่าที่จำเป็น และ Android ต้องปิด Cleartext Traffic
